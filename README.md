Banking Transaction API
A beginner-friendly REST API built with Java, Spring Boot, Spring Data JPA, and MySQL. The project demonstrates how to create and retrieve banking transaction records through HTTP endpoints and persist them in a relational database.
Demo project: This application is for learning and portfolio demonstration only. It does not move real money and is not production-ready.

Features
- Create a transaction through a REST API
- Retrieve all saved transactions
- Persist transaction records in MySQL using Spring Data JPA
- Automatically generate transaction IDs and creation timestamps
- Basic input checks for sender account, receiver account, positive amount, and transaction type
- Test endpoints using PowerShell or Postman
Tech Stack
- Java
- Spring Boot
- Spring Web / REST
- Spring Data JPA (Hibernate)
- MySQL
- Maven
- Postman or PowerShell for API testing

Prerequisites
Install the following before running the application:
- JDK compatible with the project's pom.xml
- MySQL Server
- MySQL Workbench (optional, for viewing records)
- Git (optional, for version control)
Database Setup
1. Start MySQL Server.
2. Open MySQL Workbench or a MySQL terminal.
3. Create the database:
CREATE DATABASE banking_db;
4. Configure src/main/resources/application.properties:
spring.datasource.url=jdbc:mysql://localhost:3306/banking_db
spring.datasource.username=root
spring.datasource.password=YOUR_MYSQL_PASSWORD

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
Replace YOUR_MYSQL_PASSWORD with your local MySQL password. Never commit real passwords or credentials to GitHub. For a public repository, use environment variables or a local, untracked configuration file for secrets.
Run the Application
From the project root in the VS Code terminal:
.\mvnw.cmd clean test
If tests pass, start the application:
.\mvnw.cmd spring-boot:run
Keep the server terminal open while testing. The default URL is:
http://localhost:8080
API Endpoints
Method	Endpoint	Description
POST	/api/transactions	Create and save a transaction
GET	/api/transactions	Retrieve all transactions


Create a Transaction
PowerShell example:
$body = @{
    senderAccount   = "ACC1001"
    receiverAccount = "ACC1002"
    amount          = 1500.00
    transactionType = "UPI"
    description     = "Demo payment"
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "http://localhost:8080/api/transactions" `
    -Method Post `
    -ContentType "application/json" `
    -Body $body
Example response (the ID and timestamp will be generated by the application):
{
  "id": 1,
  "senderAccount": "ACC1001",
  "receiverAccount": "ACC1002",
  "amount": 1500.00,
  "transactionType": "UPI",
  "description": "Demo payment",
  "createdAt": "2026-10-26T18:31:23"
}
Retrieve All Transactions
Invoke-RestMethod `
    -Uri "http://localhost:8080/api/transactions" `
    -Method Get
To format the output as JSON:
Invoke-RestMethod `
    -Uri "http://localhost:8080/api/transactions" `
    -Method Get | ConvertTo-Json -Depth 5
Verify Data in MySQL
Run these queries in MySQL Workbench:
USE banking_db;

SHOW TABLES;

SELECT * FROM transactions ORDER BY id DESC;

SELECT COUNT(*) AS total_transactions
FROM transactions;
Add 100 Demo Transactions
The project can be populated with synthetic transactions by sending repeated POST requests to /api/transactions from PowerShell. Use fictional account numbers and demo data only. The current API model stores sender account, receiver account, amount, transaction type, description, and creation timestamp. Separate sender/receiver names, payment status, and reference numbers require adding fields to the Java entity and updating the API before those values can be stored as dedicated columns.
Current Limitations
- Demo-only; no real banking or payment-network integration
- No authentication or authorization yet
- No account balance checks or actual money transfers
- No pagination or transaction-by-ID endpoint yet
- Payment method, status, and customer names are not separate API fields in the current model
Possible Improvements
- Add DTOs and Bean Validation
- Add GET /api/transactions/{id} and filtering/pagination
- Add dedicated fields for customer names, payment method, status, and reference number
- Add authentication and role-based authorization
- Add unit and integration tests
- Use environment variables for database credentials
- Add API documentation with OpenAPI/Swagger
- Add Docker support and CI with GitHub Actions
